# SP15f — official Lever partner application: end-to-end source path

**Status:** authorized partner-only implementation in a draft PR. No actual
employer was contacted during engineering/CI. Nothing is automatically enabled
by installing this code, and no paid GitHub workflow is required.

## Why this path

Lever's own public [Postings API documentation](https://github.com/lever/postings-api)
supports custom application submission, multipart PDF resumes and a machine
response containing applicationId on success. The POST requires an API key
generated by a Super Admin of **the employer's own Lever account**. The
Postings API does **not expose custom application questions**, and Lever
warns about rate limiting. An arbitrary job listing, scrape, source-policy
approval or SmartPloy browser companion does NOT grant API access.

**Implementation reuses** the existing SP15a atomic sticky claim; SP15c
reviewed workspace; SP15d exact contact/CV packet SHA; SP15e independent
rights attestations, two distinct reviewers and 90-second applicant approval;
existing OIDC session, CSRF, current-job preflight and PDF exporter; existing
httpx package. No Lever code has been copied or relicensed.

## Operator onboarding, per job (no bulk consent)

1. Obtain a genuine Lever admin-issued API key under a documented employer
   partner agreement that explicitly allows SmartPloy to send applications
   for the **exact** posting. Have a second authorized reviewer independently
   examine and approve the agreement and the posting's current terms.
2. Examine the actual employer-hosted application and its required fields,
   privacy/consent conditions, region and anti-abuse requirements. This
   integration supports standard name/email/PDF/phone/URLs/cover-letter only.
   **If ANY custom required questions, screening tests, special consent
   policies, manual CAPTCHA or unknown fields exist, do not activate this
   partner job.** Keep the existing manual employer-site workflow instead.
3. Record independently reviewed permission evidence in the existing
   smartploy_employer_automation_rights table for only that normalized Lever
   posting with action_scope = partner_lever_postings_api_submit (not the
   browser click channel), state approved, permission_basis
   documented_partner_integration or explicit_employer_authorization, SHA-256
   hashes of evidence and terms, two DISTINCT authorized reviewer identities
   and a limited expiry (max 90 days). SourcePolicy discovery authorization
   is explicitly insufficient.
4. Place the API secret only in the managed server environment under an
   operator-chosen name matching SMARTPLOY_LEVER_PARTNER_KEY_[A-Z0-9_]+.
   Never commit, paste in issues, return in API JSON, place in browser packet,
   or expose through client-side Vite variables.
5. Set SMARTPLOY_LEVER_PARTNER_JOBS_JSON server-side with the exact
   org/posting slug, region, key environment name and the digest of the
   reviewed standard employer form. Example with **synthetic placeholders**:

       {"example-org/example-posting-id":{
         "region":"eu",
         "api_key_env":"SMARTPLOY_LEVER_PARTNER_KEY_EXAMPLE",
         "form_review_sha256":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
         "standard_form_only_reviewed":true,
         "consent_policy_reviewed":true}}

   Without BOTH the managed job configuration/key and independent exact-job
   rights row, SmartPloy returns a blocked readiness state and never sends a
   request. The config is an operator attestation, not machine verification
   of the current live application form.
6. Run the full synthetic signed-in FastAPI/PostgreSQL/provider MockTransport
   acceptance, native ObumDelivery exact-SHA test plus negative RED probe,
   verify partner API rules/limits/backup/rollback, and owner-authorize a
   staged release BEFORE enabling a real job. No real applicant is used in CI.
   Production permission must be reviewed independently of the code.

## Applicant flow after approved deployment

- Sign in with ZITADEL, choose and review one current vacancy, save CV and
  cover letter, and record the existing 10-minute exact reviewed intent.
- Open the job's Application Studio and prepare the approved CV packet.
- For a supported partner posting only, the **Submit reviewed application to
  authorized Lever employer** button appears. The applicant reads a separate
  final confirmation naming the employer, exact reviewed documents, privacy
  terms and the fact this is an ACTUAL application. It does not send on
  application creation, AI drafting or page load.
- The FastAPI endpoint recomputes every owner/job/contact/PDF hash, rechecks
  the still-current job and exact partner rights, creates a separate 90-second
  final applicant approval, and atomically consumes that approval with the
  ORIGINAL sticky SP15a claim, before any personal data leaves SmartPloy.
- The server performs a **non-PII public GET** to Lever's fixed global/EU API
  endpoint to validate live posting ID/applyUrl. If unchanged, it performs
  ONE multipart POST with the reviewed name, email, CV PDF, phone/URLs and
  letter, including the employer-admin API credential. Redirects are off,
  destinations fixed, no external AI is involved, and no job can be retried
  automatically after any attempt.
- A 200 response with ok:true and a bounded applicationId is stored as a
  provider-issued acknowledgment, NOT proof of recruiter acceptance or a
  hiring outcome. Users can see their provider reference in their private
  Studio. A timeout, 429, 5xx, malformed response, connection error or
  interrupted receipt write stays uncertain, with no automatic retry.

## Operational boundaries and follow-up

Lever itself recommends handling 429 through queuing/retry or its hosted
application form. SmartPloy prioritizes never duplicating an uncertain
application: a 429 becomes human reconciliation rather than an automatic
retry. That may sacrifice unattended completeness and should be revisited
only if an independently proven idempotent provider flow is available.
Do not claim guaranteed delivery when the provider acknowledgment is missing.

This narrow path does not cover unsupported Lever custom questions,
Greenhouse, Workday, LinkedIn, Duunitori, Barona or public-sector portals.
Those remain source/discovery/preparation/assisted-application flows until
independently verified submission rights and adapters exist.

**Source QA and exact web/browser evidence are NOT live acceptance.**
Real partner keys, real user OIDC sign-in, protected-main promotion, native
ObumDelivery and owner-approved OVH deployment are separate release gates.
